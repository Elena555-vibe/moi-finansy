# Инструкции для агентов: «Мои финансы»

## 1. Назначение и источник истины

Этот репозиторий содержит личное мобильное PWA-приложение для контроля финансов в период строгой экономии.

Главный продуктовый источник истины — [`PRODUCT.md`](./PRODUCT.md). Перед началом любой задачи агент обязан прочитать его полностью. Подробная функциональная спецификация MVP, если файл существует, является дополнительным источником требований: `MVP_Finance_App_Specification.md`.

**Цель продукта нельзя подменять набором функций.** Приложение должно помогать пользователю:

- понимать, сколько ещё можно безопасно потратить в текущем месяце;
- соблюдать месячный лимит;
- отслеживать фактические деньги и свободные деньги;
- собирать резерв для обязательной выплаты долга.

## 2. Обязательная продуктовая сверка

Каждая новая функция, изменение существующей функции, новый экран, изменение финансовой формулы или глобальный рефакторинг должны быть сверены с `PRODUCT.md` **до реализации**.

Перед работой агент обязан кратко определить:

1. Как задача поддерживает цель продукта и решает проблему пользователя.
2. Какие продуктовые принципы и финансовые правила из `PRODUCT.md` она затрагивает.
3. Не смешивает ли она плановые и фактические деньги.
4. Не усложняет ли она ежедневный ввод или главный экран без явной пользы.

Если задача противоречит `PRODUCT.md`, заметно уводит продукт от цели, либо её влияние неоднозначно, **не додумывать решение молча**. До реализации объяснить пользователю расхождение, последствия и предложить варианты. Реализацию продолжать только после явного решения пользователя.

Если пользователь сознательно меняет стратегию продукта, сначала обновить `PRODUCT.md` и/или спецификацию, затем реализовывать изменение. Не оставлять код и продуктовые документы в противоречии.

## 3. Неприкосновенные правила финансовой логики

Без явного согласования с пользователем не менять следующие правила:

- Месячный лимит = планируемый доход − плановый резерв на долг.
- Планируемый доход не является фактическим поступлением и не меняет баланс.
- Резерв не уменьшает общий остаток, но уменьшает свободные деньги.
- Платёж по долгу уменьшает общий остаток, текущий долг и фактический резерв, но не уменьшает повседневный месячный лимит.
- Будущий платёж — это напоминание, пока пользователь не подтвердит фактическую оплату; он не влияет на баланс и лимит.
- Отрицательные финансовые показатели разрешены и должны честно отображаться, а не блокировать сохранение операции.
- Редактирование или удаление любой операции должно немедленно пересчитывать все зависимые показатели.

Финансовые формулы должны быть собраны в одном понятном доменном слое. Не дублировать расчёты в компонентах интерфейса. Для денег использовать целые рубли; не использовать `float` для денежных расчётов.

## 4. Дизайн-система

Пока дизайн-система отсутствует, не изобретать окончательную визуальную систему и не жёстко зашивать цвета, шрифты, отступы и другие визуальные значения в отдельных экранах. Использовать централизованные токены/переменные, чтобы дизайн можно было заменить без массовой переделки.

В проекте уже есть утверждённая дизайн-система: [`DESIGN_SYSTEM.md`](./DESIGN_SYSTEM.md). Связанные утверждённые визуальные ориентиры и иконка находятся в [`design-system/`](./design-system/). Они являются обязательными источниками истины для интерфейса.

Агент обязан для **каждой** новой или изменяемой фичи и **каждого** экрана:

- прочитать применимые правила дизайн-системы;
- использовать её токены, компоненты, типографику, иконки, состояния и правила адаптивности;
- не создавать визуальные исключения без согласования;
- проверить результат на соответствие дизайн-системе до передачи пользователю.

Если требуемого компонента или состояния в дизайн-системе нет, сообщить пользователю о пробеле и предложить минимальное согласованное расширение, а не создавать несвязанный стиль.

## 5. UX и границы MVP

- Приоритетная платформа: iPhone / Safari / вертикальная ориентация / PWA.
- Главная должна сохранять фокус на крупном показателе «Осталось потратить» и не перегружаться второстепенными виджетами.
- Поля обычных операций должны оставаться минимальными.
- Интерактивные области — не меньше 44 × 44 px; формы не должны ломаться из-за экранной клавиатуры или safe area.
- Приложение должно работать офлайн и не требовать авторизации в текущем MVP.
- Не добавлять в MVP банковские интеграции, облачную синхронизацию, экспорт, несколько счетов/валют, расширенную аналитику, подкатегории, комментарии, push-уведомления или другие исключённые возможности без отдельного согласования. Полный список находится в `PRODUCT.md`.

## 6. Рабочий процесс и качество

1. Сначала прочитать `PRODUCT.md`, применимые спецификации и дизайн-систему (когда она появится).
2. Проверить текущее состояние проекта и не перетирать пользовательские или чужие незавершённые изменения.
3. Реализовать минимальное решение, необходимое для согласованной задачи.
4. Проверить изменённую функциональность: финансовые расчёты, CRUD, граничные даты, отрицательные значения, мобильную вёрстку и офлайн-поведение — в объёме, соответствующем изменению.
5. Сообщить пользователю, что сделано, какие проверки выполнены и есть ли продуктовые решения, требующие внимания.

Для изменения финансовой логики обязательно добавить или обновить автоматические тесты на формулы и крайние случаи. Ошибки не должны приводить к потере уже сохранённых локальных данных.

## 7. Документация

- `PRODUCT.md` — краткий постоянный контекст и продуктовые ограничения; поддерживать его актуальным при согласованной смене направления.
- `MVP_Finance_App_Specification.md` — подробный PRD/спецификация, если пользователь решит сохранить его.
- Не удалять, не переименовывать и не перемещать продуктовые документы без явной просьбы пользователя.
- При значимой реализации обновлять релевантную документацию, если поведение продукта меняется.

## 8. GitHub и публикация

После того как согласованный объём разработки завершён, проверки пройдены и пользователь явно подтвердил готовность к публикации, агент должен самостоятельно:

1. проверить состав изменений;
2. подготовить понятный коммит, включающий только относящиеся к задаче файлы;
3. отправить изменения в GitHub;
4. при необходимости создать draft PR согласно выбранному процессу проекта;
5. сообщить пользователю ссылку и итог публикации.

**Не выполнять commit, push или создание PR без явного согласования пользователя в текущем контексте.** Доступ к GitHub не означает разрешение публиковать незавершённую или несогласованную работу.

## 9. Файлы проекта

- Все файлы в `sources/` — синхронизированные справочные материалы. Считать их только для чтения: не редактировать, не переименовывать, не перемещать и не удалять.
- Не выполнять разрушительные операции (`reset --hard`, массовое удаление, очистку хранилища) без прямой просьбы пользователя.
